# 真实 NAT VPS 无 swap 验证记录

> 公开归档：测试日期为 2026-11-08，2026-11-09 上传。凭据、主机地址及生产用户的具体流量数据不公开；合成测试计数、失败记录和测量结果保留。

> 本阶段只验证节点本地计数和 API；主站倍率入账见[后续联调报告](../2026-11-08-master-accounting/REPORT.md)。

日期：2026-11-08。测试对象为已发布的轻量节点 v0.1.1，以及官方 Xray v26.10.31。本次没有重新编译或修改 Xray，也没有发布新的节点版本。

结论：两台真实 NAT VPS 在默认 32 KiB TCP 缓冲配置、无 swap 条件下，完成了普通 VLESS / TLS 的 1、8、32 路突发下载，并各通过了额外 4 轮 32 路 TLS 下载（各 1 GiB）。但是，取消缓冲限制的对照测试导致了断流、OOM 或容器重启，不能推荐给这两种低内存配置。默认设置在其中一条高延迟线路上明显降低了单连接吞吐。

## 环境与测量范围

| 项目 | 节点 1 | 节点 2 |
| --- | --- | --- |
| 系统 | Alpine 3.21.10 / OpenRC | Debian 13 / systemd |
| 商家标称内存 | 128 MB | 64 MB |
| 实际 cgroup 内存上限 | 128,000,000 字节，约 122.07 MiB | 67,108,864 字节，64 MiB |
| swap | 原本禁用 | 测试前将容器 memory.swap.max 从 64 MiB 改为 0 |
| 实际 swap 使用 | 所有已采样测试区间均为 0 | 所有已采样测试区间均为 0 |
| 额外已有服务 | Komari agent 等，保留运行 | systemd、journald、SSH 等，保留运行 |
| 安装方式 | 临时 OpenRC 服务 | 采用发布包和原包 systemd unit 安装 |

节点 2 在无缓冲限制的故障测试后重启，宿主机重新赋予了 64 MiB 的 swap 额度；发现后立即再次设为 0，恢复测试开始前已核实。没有在启用 swap 的状态下执行恢复压测。目前两台的 memory.swap.max 和 memory.swap.current 均为 0。宿主机可能在下次容器重启时重新设置额度，本次没有修改商家宿主机配置。

测量读取容器根 cgroup 的 memory.current，每约 0.2 秒采样，包含系统、SSH、现有服务、x-ui、原版 Xray、约数 MiB 的临时下载源和采样程序。没有使用可能显示宿主机容量的 free 数字作为 VPS 用量。数值包含可回收文件缓存，不能等同于程序不可回收内存；采样也可能遗漏不足 0.2 秒的峰值。

客户端放在用户提供的较大 VPS 上，以独立 systemd 单元运行，限制 CPU 为半核、低优先级；未调用生产面板的配置修改接口。客户端仅通过两台测试节点的 HTTPS Bearer API 创建和删除测试入站，并验证下载的节点证书。流量走公网映射，不是本机回环模拟。节点出站只为测试额外允许本机 50003 下载源，结束后恢复原配置。

负载为一个合成 VLESS 用户，TCP 普通传输与 TLS；常规各并发每连接 4 MiB，恢复轮每连接 8 MiB。每个临时下载源实例总量上限 2 GiB，最多 40 个连接。没有测试 REALITY、UDP、多用户规模或数小时持续负载。

## 默认设置结果

| 项目 | 节点 1：128 MB | 节点 2：64 MiB |
| --- | ---: | ---: |
| 单连接普通 VLESS | 2.69 Mbps | 20.07 Mbps |
| 单连接 VLESS TLS | 2.66 Mbps | 16.57 Mbps |
| 32 路普通 VLESS，总吞吐 | 82.99 Mbps | 362.21 Mbps |
| 32 路 VLESS TLS，总吞吐 | 77.41 Mbps | 328.02 Mbps |
| 常规代理测试请求数 | 82 | 82 |
| 常规代理请求失败 | 0 | 0 |
| 常规代理阶段整机采样峰值 | 69.39 MiB | 63.97 MiB |
| 额外恢复验证 | 4 × 32 路 TLS，共 1 GiB | 4 × 32 路 TLS，共 1 GiB |
| 恢复验证请求失败 | 0 / 128 | 0 / 128 |
| 恢复验证整机采样峰值 | 71.64 MiB | 63.88 MiB |
| 默认及恢复测试新增 OOM kill | 0 | 0 |

节点 2 的数秒突发测速超过商家标称 200 Mbps，记录的是本轮应用有效载荷除以实际耗时，不能当成长期可用带宽承诺。网络路径、商家突发策略、客户端限制都会影响结果；两台机器之间也不能直接比较内存配置对网速的因果影响。

64 MiB 虽然完成本轮负载，memory.events 的 max 计数仍增长，说明已多次触及内存上限并回收缓存。它的余量很小，不能保证再增加用户、连接、其他程序或换协议仍然稳定。

移除测试入站和辅助程序后，节点 1 整容器约 56.5 MiB；节点 2 约 63.5 MiB，后者包含约 40.6 MiB 文件缓存。随后读取进程 RSS：节点 1 的 x-ui / Xray 分别约 10.2 / 18.3 MiB；节点 2 分别约 14.5 / 20.7 MiB。进程 RSS 随缓存和采样时间变化，不能把全部 RSS 简单相加后视为独占物理内存。

## 缓冲与网速的对照

同一节点 1，保持 Xray 二进制和网络路径不变，仅调整节点的 socketBufferKB：

| TCP 缓冲设置 | 单连接普通 / TLS | 32 路 TLS | 整机采样峰值 | 稳定性 |
| --- | --- | --- | --- | --- |
| 默认 32 KiB | 2.69 / 2.66 Mbps | 77.41 Mbps | 常规 69.39 MiB | 本轮通过 |
| 有上限的 128 KiB | 6.08 / 5.74 Mbps | 80.09 Mbps | 82.71 MiB | 82 个代理请求均通过，无新增 OOM |
| 不设置上限，由内核自动调节 | 20.48 / 16.99 Mbps | 32 / 32 失败 | 接近 122 MiB 上限 | 发生 OOM |

节点 1 的普通 32 路无上限测试也有 32 / 32 请求失败；整个无上限阶段 memory.events 记录 oom=4、oom_kill=3，已有 Komari agent 也被迫重启。测试后确认它已自动恢复运行。没有从内核日志取得每个被杀进程的完整清单，因此不能把全部 OOM 都归因于某一个进程。

节点 2 在无上限的普通 32 路测试中出现 27 / 32 请求失败，随后 API 和 SSH 连接断开，容器 uptime 归零、服务停止。重启前的 OOM 计数没有持久保留，因此能确认的是“负载期间容器重启”，不能声称已取得该次重启的 OOM 根因证明。后来恢复默认配置、再次禁用 swap 后，4 轮 32 路 TLS 均通过。

这个对照说明：较小缓冲能减少突发内存，但会在部分高 RTT 线路上降低单连接速度。128 KiB 是本轮节点 1 上有改善的候选值，尚未验证它在 64 MiB 或长时间运行下的稳定性，不能直接改成所有节点的默认值。本次结束后两台均恢复 32 KiB 默认。

## 测试自身的问题与处理

- 最早的节点 1 直连源固定使用 16 KiB 发送缓冲，这会限制直连基准。该阶段保留为 direct-source-16KiB 原始数据，但不作为正常直连参考。随后修正下载源：公网直连由内核自动调节；回环源仍固定 16 KiB。修正后的节点 1 单连接直连为 19.02 Mbps。
- 最初节点 2 的 1 GiB 恢复验证中，发生器自己的 96 MiB systemd 单元被 OOM 杀死，未生成完整轮次结果；当时节点仍健康且无新增 OOM。此无效轮次没有计入通过结果。确认主站仍有约 1.2 GiB 可用内存后，把发生器单元上限改为 384 MiB，保持半核限制和低优先级，重新完整执行 4 轮并通过。这个上限仅属于测试客户端，未提高任何 NAT 节点内存上限。
- Debian 从 GitHub 直接下载节点发布包多次返回 HTTP 504，因此改用本地已校验发布包经 SSH 上传。不能把本次写成一键联网安装器完整通过。
- Alpine 使用了单独的临时 OpenRC 启动脚本，不能据此声称当前公开 systemd 安装脚本已经支持 Alpine。

## 生产主站与清理

生产 x-ui 全程 MainPID=437、NRestarts=0，没有升级、重启或写生产数据库。数据库确认实际使用 PostgreSQL，只执行 BEGIN READ ONLY 查询。检查期间管理员行、入站、节点和流量记录行数保持不变；流量总量随真实用户使用继续增长，没有被本测试归零。具体生产聚合数据仅在本地私有记录中保存，不作为公开性能附件。

两台测试节点的临时 VLESS 入站均已通过 API 删除，50002 和 50003 不再监听；下载源和采样程序已停止。API 50001 保留运行。测试专用回环出站规则已移除，原配置已恢复；节点健康检查通过。生产主站上的所有流量发生器已停止，临时节点凭据已删除。测试用 API 密钥和证书私钥未写入本报告。

常驻管理进程名称仍为 x-ui，核心进程为 xray。两台 x-ui 均对应原发布包，SHA256 为 `069649990231ef78dcd9171867dc621f1bf5bcb97e98812941f724ad1730ea7b`；原版 Xray 二进制 SHA256 为 `cc4b84d3069569f297a61f04b914f2bb37e9d202fd7b84cb50def1fc30fd40e1`。

## 交付范围与未完成验收

这是实机内存、无 swap、突发下载和节点 API 控制测试，不是两套产品全部功能的生产验收。当前仍不应声称“所有功能已测试无问题”：

- 实际生产 PostgreSQL 主站的独立升级保数据流程，尚未做升级实测；此前 SQLite 验证不覆盖它。
- 删除节点导致其他用户流量清空的问题，本轮未在生产复现或修复。
- TG 节点离线告警尚未交付。
- v0.1.0 更名迁移后，旧升级器路径更新遗漏的问题尚未修复。
- 本轮没有通过生产主站添加测试节点，没有新增生产用户，也没有在生产执行删除节点或重置流量操作。

建议：128 MB 优先；64 MiB 仅适合经过具体协议与负载验证的小规模使用。保留缓冲上限，不能为了提速完全取消。是否采用 128 KiB 候选值，应单独评估用户数、延迟、连接数和内存余量。
