# 主站接收、倍率计费与 NAT 高并发联调实测

> 公开归档：测试日期为 2026-11-08，2026-11-09 上传。凭据、主机地址及生产用户的具体流量数据不公开；合成测试计数、失败记录和测量结果保留。

日期：2026-11-08。测试节点：轻量节点 v0.1.1，官方 Xray 26.10.31，Komari 保持运行，swap 限额和使用量均为 0。

**结论：本轮两台节点的最终原始流量、主站接收基线、2.5 倍计费、回推账单均核对通过。128 MB 的本轮传输与健康检查通过；64 MiB 在高压下仍出现整轮下载失败和明显统计延迟，不能保证实时同步或稳定使用。**

## 验证范围与生产保护

使用当前生产主站程序的副本，SHA256 为 `c500bf1b46d4f16b95c87b4906915b2413f37b25b9b24af8314979da66d4b148`，与生产运行文件一致。测试主站使用独立 PostgreSQL 15 实例、独立数据目录、独立 Unix socket 和仅监听回环地址的管理端口。没有复制生产用户、数据库、节点密钥或配置。测试进程设有独立 CPU/内存限制，生产目录在测试服务的文件系统视图中不可访问。

两台 NAT 均未注册在生产主站中。测试主站通过公网 HTTPS、Bearer 密钥及固定证书 SHA256 连接节点，由主站创建入站和每台 10 个合成账号。首次原始基线归零并建立后才发送流量。使用 VLESS TCP + TLS，每条请求下载并校验 2 MiB 内容，经 NAT 公网映射连接，节点访问自己的临时受限下载源。

本轮验证了**同一生产程序、同一种数据库后端的隔离账务链路**。生产站仅做只读检查，未拿现有真实用户进行逐笔对账；因此不能把本轮结果写成“生产所有节点、所有用户、所有功能均无误”。

| 项目 | 标称 128 MB（实际 122.07 MiB 上限） | 64 MiB |
| --- | --- | --- |
| 并发 | 40 / 80 / 160，各两轮 | 40 / 80，各两轮 |
| 请求总数 | 560 | 240 |
| 完整下载失败 | 0 | 80，全部来自第二轮 80 并发 |
| 健康接口检查 | 40 次，0 次失败 | 14 次，11 次失败 |
| 最高档 P95 首字节 | 两轮 0.962 / 1.112 秒 | 两轮 20.303 / 34.264 秒 |
| 整个采样窗口内存峰值 | 103.89 MiB | 63.99 MiB |
| 新增 OOM kill | 0 | 0 |
| swap 最大使用 | 0 | 0 |
| 最终 10 个账号核账 | 通过 | 恢复后通过 |

内存包含系统、探针、x-ui、Xray、SSH、临时下载源和采样程序；约每 0.5 秒取样，不能覆盖所有瞬时峰值。128 MB 此次健康接口无失败，不会推翻上一轮出现过短暂 `config_busy` 的记录，也不构成长期零故障保证。

64 MiB 第二轮 80 并发有 76 次超时、4 次连接中止。健康接口失败包括 6 次 Xray stats 超时、3 次配置锁忙及 2 次未分类传输错误。没有 OOM 或自动重启，并不代表用户体验正常。

## 主站是否收到并正确计费

在独立测试数据库中，为原始同步基线增加审计触发器，记录每次更新的前后值。最终导出 2,040 条审计记录，并在本地用整数运算独立重算每次增量的 2.5 倍取整结果。**两台共 20 个合成账号，上行和下行的计费结果均逐字节一致，允许误差为 0。**

| 下行指标（字节） | 128 MB 节点 | 64 MiB 节点 |
| --- | ---: | ---: |
| 客户端实际收到的有效载荷 | 1,174,405,120 | 377,127,554，包含失败请求收到的部分数据 |
| 节点原始计数 = 主站原始基线 | 1,174,440,400 | 379,196,397 |
| 主站倍率账单 = 节点收到的全局账单 | 2,936,101,002 | 947,990,996 |

节点原始计数包含 HTTP 请求/响应及实际写入连接的数据，因此不等于有效载荷；失败请求中已经由代理发出但未全部被客户端读取的数据，也不能直接按完整下载次数推算。倍率按每次同步增量取整，合计值可能比“最终原始总量直接乘 2.5”多几个字节；本轮差异完全由逐次取整解释。

核对内容包括：每个账号的节点 raw 值与主站 raw 基线完全一致、主站 API 与数据库账单一致、节点收到的全局账单与主站账单一致、原始计数没有被倍率回推污染。128 MB 的 106 个采样和 64 MiB 的 79 个采样均未发现计费公式不一致。

**64 MiB 的同步并非实时正常。** 主站原始下行基线曾约 129 秒没有更新；最后一轮负载结束约 46 秒后，采样才看到最终值。压力缓解后计数补齐，并在后续 15 秒稳定等待及 36 秒静置检查中保持不变，没有再次入账。128 MB 同样完成了 36 秒静置检查。

64 MiB 初轮脚本只检查“节点计数等于主站基线”，两边同时陈旧时会过早认为已经同步。随后空闲期间补记真实流量，触发了脚本中的 `idle_double_billing` 断言。原始失败日志保留。收尾验证已增加客户端实际接收量的下限及稳定等待；审计记录证明这次增加来自原始流量补齐，并非重复计费。128 MB 全程使用加严后的逐用户有效载荷下限。64 MiB 失败轮只保存了合计有效载荷，因此恢复验证使用合计下限，加上各用户成功轮至少 32 MiB 的下限；不声称已逐个还原失败请求的完整字节账。

## 生产站与清理结果

- 生产 `x-ui` PID 始终为 437，自动重启次数始终为 0，程序文件未变。
- 只读检查中，管理员、入站、节点和用户流量记录前后数量一致；生产记录的具体数量不随公开附件发布。
- `client_traffics` 上下行合计均继续增长；公开报告不披露生产用户的具体流量。本轮没有写入生产数据库、清零用户流量或重启生产主站。
- 生产节点在测试前后都是 7 个在线、1 个离线。**该节点的离线状态在本轮测试前已存在，本轮未处理该既有故障。**
- 已删除测试账号所在的临时入站，恢复两台 NAT 原配置，停止临时下载源与采样。50002 / 50003 不再监听；50001 管理 API 正常，Xray 运行，临时入站数量为 0，常驻进程名仍为 `x-ui`。
- Komari 保留运行。测试期间节点管理服务和探针未自动重启；配置恢复时对测试节点执行了手动重启。
- 隔离主站、隔离 PostgreSQL、临时 systemd 单元及本轮远程测试目录均已移除，SSH 测试会话关闭。

本轮没有修改或发布产品代码。未覆盖长时间运行、UDP、真实互联网目标、多主站同时接入、节点崩溃后的持久化恢复、额度耗尽停用、生产 PostgreSQL 升级、删除节点清流量问题或 Telegram 离线通知验收。

## 本地证据

- `results.json`：两台汇总结果。
- `evidence/`：原始请求记录、同步审计、内存 CSV、只读生产汇总及恢复后的健康检查。

- `summarize.py`：独立整数重算和三方账单断言，将本目录的 `evidence.zip` 解压到一个新目录后，进入该目录执行 `python summarize.py` 复核；它只读取证据，不连接 VPS。
- `evidence.zip`：仅包含报告、脱敏证据和测试脚本，不含 SSH 密码、API token、私钥、数据库连接串或完整节点状态。
